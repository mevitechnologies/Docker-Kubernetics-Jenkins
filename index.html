CORE CONCEPTS

Every tool: what it is, why it exists, and what it does

How to think about the complete system: Git keeps a history of source-code changes. GitHub stores a shared copy of that repository. Jenkins reads a selected revision and runs repeatable pipeline steps. Docker turns the application and its runtime requirements into an image, then runs that image as a container. Kubernetes manages containers across Pods, keeps the requested number of replicas running, and provides a stable way to reach them. These tools solve different problems; they work together rather than replacing one another.

Why?Track changes, compare versions, work on branches, and recover earlier work.

An automation server that runs jobs and pipelines for building, testing, and delivering software.

Why?Replace repetitive manual build steps with a repeatable process.

Find Jenkins images

Remember this one-line summary: Git records code → GitHub shares code → Jenkins automates steps → Docker packages and runs the app → Kubernetes manages application replicas and access.

CI — Continuous Integration

Continuous Delivery

The software is automatically built and prepared for release, usually with an approval before production.

git remote -v
git push -u origin main

Replace YOUR-USERNAME. A remote is a saved address to another repository; origin is its usual nickname; push uploads local commits.

PART 3 · CONTAINERISE

Docker + Nginx: package and host the website

NginxServes the page

What is Nginx and why are we using it?

Nginx (pronounced “engine-x”) is web-server software. A browser sends an HTTP request; Nginx looks for the requested file and sends an HTTP response. It can also be configured as a reverse proxy or load balancer. Here, it serves our static index.html and style.css.

Why not open the file only? Opening a file checks the page locally, but running Nginx in a container demonstrates how a web server hosts the content on a network port.

Open image search: how Nginx works
09

Create a Dockerfile

WHERE: VS Code editor → project root → New File → Dockerfile
FROM nginx:alpine
COPY index.html /usr/share/nginx/html/index.html
COPY style.css /usr/share/nginx/html/style.css
EXPOSE 80
  • FROM: choose the base image containing Nginx.
  • COPY: copy our two website files into Nginx's default web directory.
  • EXPOSE 80: documents that the container expects web traffic on port 80; it does not publish the port to the host by itself.
10

Build the image

WHERE: VS Code terminal → project root
docker build -t devops-site:1.0 .
docker image ls

Break down the command: docker build builds an image; -t gives it a name and tag; devops-site:1.0 is the image name/version; the final dot means “use this current folder as the build context”.

Expected: the build finishes successfully and docker image ls lists devops-site.

11

Run the container and publish a port

WHERE: VS Code terminal
docker run --name site-manual -d -p 8085:80 devops-site:1.0
docker ps
Your computerHost port 8085localhost:8085
8085 → 80
ContainerNginx port 80Serves index.html

Open http://localhost:8085 in the browser. If your page appears, the website is hosted locally.

Why map ports? The server listens on port 80 inside the container. -p 8085:80 makes it reachable through port 8085 on your computer.

12

Clean up before Jenkins deployment

WHERE: VS Code terminal
docker rm -f site-manual

We will let Jenkins create a container with a different name. Removing this manual test container prevents a conflict on port 8085. The image remains available.

PART 4 · AUTOMATE

Jenkins: installation, working, and pipeline

JenkinsAutomation server

How Jenkins works

  1. A developer pushes a commit to GitHub.
  2. Jenkins checks out the selected version of the source code.
  3. A Pipeline runs its stages in order, such as validation, tests, and Docker build.
  4. The pipeline records console output and reports success or failure.
  5. In this classroom lab, a final stage starts the website container on the Docker host.
Open image search: Jenkins pipeline workflow
Job

A configured unit of work Jenkins can run.

Pipeline

A defined sequence of stages and steps.

Jenkinsfile

A text file that stores the pipeline definition alongside the source code.

Build

One execution of the job or pipeline.

Security and platform note: To build Docker images from inside Jenkins, Jenkins needs access to a Docker daemon. Mounting /var/run/docker.sock is a convenient classroom shortcut on many Docker Desktop setups, but it gives Jenkins powerful control over the host's Docker engine. Use it only on a trusted disposable learning guide environment; do not run untrusted pipeline code this way. The official Jenkins documentation also describes a Docker-in-Docker setup using a separate Docker daemon and TLS.
13

Create a custom Jenkins image with Docker CLI

WHERE: VS Code Explorer → create folder jenkins → create jenkins/Dockerfile
FROM jenkins/jenkins:lts-jdk21
USER root
RUN apt-get update \
    && apt-get install -y --no-install-recommends docker.io \
    && rm -rf /var/lib/apt/lists/*
USER jenkins

The official Jenkins image is the base. The Docker CLI package adds the docker command inside the Jenkins container. The daemon itself is not installed by this Dockerfile; the next step mounts the host Docker socket for this local lab.

Note: this simple classroom Dockerfile uses the distribution's Docker CLI package. If package installation fails or the client cannot talk to the host daemon, follow the official Jenkins Docker installation guide linked at the bottom.

14

Build and run Jenkins

WHERE: VS Code terminal → project root
docker build -t mevi-jenkins-lab:1.0 ./jenkins
docker volume create jenkins_home
docker run -d --name jenkins-\
  -p 8080:8080 -p 50000:50000 \
  -v jenkins_home:/var/jenkins_home \
  -v /var/run/docker.sock:/var/run/docker.sock \
  mevi-jenkins-lab:1.0

What the options mean: port 8080 is Jenkins' browser UI; 50000 is commonly used for inbound agents; jenkins_home is a named volume that preserves Jenkins settings and jobs; the socket mount gives Jenkins access to the host Docker engine.

Check: run docker ps and wait for the Jenkins container to be running. Open http://localhost:8080. First startup may take a few minutes.

If port 8080 is already in use, change the left side to another host port, for example -p 8089:8080, then open http://localhost:8089. The Jenkins internal port remains 8080.
15

Unlock Jenkins

WHERE: VS Code terminal, then browser
docker exec jenkins-cat /var/jenkins_home/secrets/initialAdminPassword

Copy the printed initial password into the unlock screen. Install suggested plugins and create an administrator account. Keep the password private. Jenkins stores its configuration under JENKINS_HOME, which is why the named volume matters.

16

Check Docker access from Jenkins

WHERE: VS Code terminal
docker exec jenkins-docker version

The output should show client and server details. If it says it cannot connect to the daemon, stop here and fix access before creating the pipeline.

PART 5 · JENKINSFILE

Build the automated CI/CD pipeline

We will use a Pipeline job that reads a Jenkinsfile from the GitHub repository. The pipeline checks out the source, verifies files, builds the image, and runs the website.

STAGE 1CheckoutFetch source
STAGE 2ValidateCheck files
STAGE 3BuildCreate image
STAGE 4DeployRun container
17

Create Jenkinsfile

WHERE: VS Code editor → project root → New File → Jenkinsfile

Replace YOUR-USERNAME with your GitHub username. The repository should be public for this simplest no-credentials example; private repositories need credentials configured securely in Jenkins.

pipeline {
    agent any

    environment {
        IMAGE_NAME = 'devops-site:1.0'
        CONTAINER_NAME = 'site-ci'
    }

    stages {
        stage('Checkout') {
            steps {
                git branch: 'main',
                    url: 'https://github.com/YOUR-USERNAME/devops-site.git'
            }
        }

        stage('Validate files') {
            steps {
                sh 'test -f index.html'
                sh 'test -f style.css'
                sh 'test -f Dockerfile'
                echo 'Required files are present.'
            }
        }

        stage('Build Docker image') {
            steps {
                sh 'docker build -t ${IMAGE_NAME} .'
            }
        }

        stage('Deploy website') {
            steps {
                sh 'docker rm -f ${CONTAINER_NAME} || true'
                sh 'docker run -d --name ${CONTAINER_NAME} -p 8085:80 ${IMAGE_NAME}'
            }
        }
    }

    post {
        success {
            echo 'Success. Test the site at http://localhost:8085 on the Docker host.'
        }
        failure {
            echo 'Pipeline failed. Open the failed build Console Output and inspect the first error.'
        }
    }
}

Explain the syntax: pipeline is the pipeline definition; agent any asks Jenkins to use an available agent; environment stores reusable values; each stage groups related work; steps run commands; post handles success/failure messages.

This example is intentionally a simple classroom pipeline. It uses a fixed image tag and deploys on the same Docker host. Real CI/CD should add tests, immutable version tags, a registry, secure credentials, approvals, health checks, and a safe deployment strategy.

PART 6 · ORCHESTRATE

Kubernetes in Docker Desktop: detailed practical tutorial

KubernetesContainer orchestration

What Kubernetes does

Kubernetes watches the actual state of an application and tries to make it match the desired state described in manifests. For example, if a Deployment requests two Pods, Kubernetes works to keep two suitable replicas running. If a Pod fails, a controller can replace it. A Service provides a stable way to reach a changing set of Pods.

Open image search: Kubernetes architecture

Why do we need Kubernetes after Docker?

Docker alone

  • Build and run individual containers.
  • You manually start/stop and manage many instances.
  • Networking and recovery need to be configured for your app.

Kubernetes

  • Declares the desired state for workloads.
  • Maintains the requested number of replicas.
  • Provides Deployments, Services, rollouts, and workload management.

Kubernetes terms you must understand

Cluster

The Kubernetes environment that manages workloads.

Node

A machine or worker environment that runs Pods.

Pod

The smallest deployable unit; often contains one app container.

Deployment

Declares the desired app version and replica count.

Service

A stable network endpoint that routes to matching Pods.

Manifest

A YAML/JSON declaration of resources and desired configuration.

22

Check kubectl and the current cluster

WHERE: VS Code terminal
kubectl version --client
kubectl config get-contexts
kubectl config current-context
kubectl get nodes

kubectl is the command-line client for the Kubernetes API. A context identifies which cluster and credentials kubectl will use. The node should show Ready when the cluster is ready.

If the intended local context is named docker-desktop and appears in the context list, select it with kubectl config use-context docker-desktop. Do not change contexts blindly if you also use a work or cloud cluster.

23

Build the image for Kubernetes

WHERE: VS Code terminal → project root
docker build -t devops-site:1.0 .
docker image ls devops-site

Kubernetes needs to be able to obtain the image. Depending on Docker Desktop version and cluster runtime, a locally built image may or may not be visible to the cluster. If a Pod reports ImagePullBackOff, inspect Pod events; use a registry or the supported image-loading method for your cluster.

24

Create a Kubernetes manifest

WHERE: VS Code Explorer → create folder k8s → create file site.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: website
          image: devops-site:1.0
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: web-service
spec:
  type: NodePort
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80
      nodePort: 30080

Deployment section: asks for two replicas, selects Pods with label app: web, and starts the website container from the named image.

Service section: finds Pods with the same label and forwards traffic to port 80. nodePort: 30080 requests a NodePort for this local exercise.

YAML rule: indentation matters. Use spaces, not tabs. Save the file.

25

Apply the manifest and inspect resources

WHERE: VS Code terminal → project root
kubectl apply -f k8s/site.yaml
kubectl get deployments
kubectl get pods
kubectl get services
kubectl describe deployment web

Expected: Deployment reports ready replicas; Pods become Running and READY 1/1; Service is listed with port information. Wait a little after applying; image startup is not always instant.

If a Pod is not ready, run kubectl describe pod POD-NAME and read the Events section. Replace POD-NAME with the actual name from kubectl get pods.

26

Open the Kubernetes-hosted page

WHERE: Browser

Try http://localhost:30080. Accessing NodePort from the host can vary with Docker Desktop versions and cluster configuration.

Reliable diagnostic option: if the NodePort URL does not open, run this in a separate terminal and leave it running:

kubectl port-forward service/web-service 8086:80

Now open http://localhost:8086. The terminal running port-forward must remain open until you finish testing.

27

Scale the Deployment

WHERE: VS Code terminal
kubectl scale deployment/web --replicas=3
kubectl get pods -o wide
kubectl scale deployment/web --replicas=2

Scaling changes the desired number of replicas. Kubernetes reconciles the actual state toward that desired count. You should see a third Pod appear, then disappear when scaling back to two.

28

Practice an update and rollback

WHERE: VS Code terminal

First change a visible sentence in index.html. Then build a new tag and update the Deployment:

docker build -t devops-site:1.1 .
kubectl set image deployment/web website=devops-site:1.1
kubectl rollout status deployment/web
kubectl rollout history deployment/web

For rollback practice, use kubectl rollout undo deployment/web. Ensure the cluster can access image tag 1.1; if it cannot see local images, load/push the image using the method supported by your cluster runtime.

29

Clean up Kubernetes resources

WHERE: VS Code terminal
kubectl delete -f k8s/site.yaml

This deletes the Deployment and Service defined in that manifest. It does not uninstall Kubernetes from Docker Desktop. You can stop the Jenkins container later with docker stop jenkins-; do not delete the jenkins_home volume unless you intentionally want to remove Jenkins' saved setup.

DEBUGGING PLAYBOOK

Common errors: exact checks and fixes

Open Docker Desktop, wait until its engine is running, then retry docker info. Fix Docker startup before troubleshooting Jenkins or Kubernetes.

Run docker ps and inspect the PORTS column. Stop/remove only the lab container using the port, or change the host side of the mapping, e.g. -p 8087:80, then open http://localhost:8087.

Run docker ps -a. If the named container is an old lab resource you no longer need, remove that specific one with docker rm -f NAME. Do not remove unrelated containers.

Check git status, git remote -v, and the branch name. Authenticate through GitHub's supported browser/credential flow. Do not put passwords or tokens in the repository. If histories differ, inspect before merging; do not blindly force-push.

Check the repository URL and branch. A public repository is simplest for class. A private repository needs a credential stored in Jenkins and referenced securely; never hard-code an access token in a Jenkinsfile.

Check the custom image build output and run docker exec jenkins-docker version. If the CLI was not installed, rebuild the custom Jenkins image and recreate its container while retaining the jenkins_home volume.

Run docker exec jenkins-docker version. Verify the Docker socket setup is supported by your environment. Do not mount arbitrary host paths or use untrusted pipeline code to work around this. The official Jenkins Docker guide describes an alternative Docker-in-Docker approach.

Run kubectl describe pod POD-NAME and read Events. Check spelling/tag. Kubernetes may not see a locally built image in every Docker Desktop cluster/runtime. Use a registry or the supported image-loading method, then update the manifest.

Wait for the cluster to finish starting. Run kubectl config get-contexts, kubectl config current-context, and kubectl get nodes. Select the intended local context only if it exists and is the correct cluster.

Check kubectl get pods and kubectl get services. Confirm the Pods are ready and Service selectors match the Pod labels. Try kubectl port-forward service/web-service 8086:80 and open http://localhost:8086.

The existing image does not change when you edit a source file. Rebuild the image with a new tag, then recreate the Docker container or update the Kubernetes Deployment to the new tag. Refresh the browser after deployment.
